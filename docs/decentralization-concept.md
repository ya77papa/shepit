# Шепіт без центру — концепція

Статус: **концепція, нічого не реалізовано.** Дві цілі, обидві обов'язкові:

1. **Стійкість.** Шепіт не можна вимкнути чи заблокувати, вимкнувши або заблокувавши один сервер
   чи домен.
2. **Метадані.** Жоден сервер, зокрема наш власний, не знає, хто з ким спілкується.

## Що вже є

- Наскрізне шифрування (Signal) і sealed sender: сервер не бачить вмісту й не знає відправника.
- Скринька адресата — `SHA-256("shepit-mailbox-v0" ‖ ідентичність)`: сервер не знає імені,
  але **знає, що це завжди та сама людина**, бачить її IP і час, коли вона забирає пошту.
- Mesh (docs/mesh-concept.md): телефони обмінюються конвертами без сервера; шлюз — пакет,
  зашифрований ключем сервера (P-256), який може донести будь-хто.

Слабкі місця зараз: один сервер (`shepit.razom.isroot.in`) і один домен; сервер бачить IP
відправника й скриньку адресата в одному запиті; сповіщення будять конкретну скриньку.

## Ідея в одному абзаці

Багато незалежних серверів, будь-який з них приймає конверт для будь-кого й пересилає далі
(федерація) — так зникає єдина точка відмови. Запити йдуть **через два різні сервери**: перший
бачить, хто ти (IP), але не бачить, куди; другий бачить скриньку, але не бачить, хто ти
(як Oblivious HTTP). Скриньки — не одна на людину, а **окрема для кожної пари контактів і
змінюється щодня**, тож сервер не може скласти «скриньки Павла». Коли обидва телефони онлайн —
вони можуть говорити напряму, і сервер не бере участі взагалі.

## 1. Багато серверів (стійкість)

- **Адреса людини** не змінюється: це ключ ідентичності. До неї додається список серверів, де
  лежить її скринька («домашні» сервери, 1–3 штуки) — він передається в запрошенні й у профілі.
- **Будь-який сервер Шепоту приймає конверт** для скриньки на іншому сервері й пересилає його туди
  (сервер-сервер, підписано ключем сервера). Заблокували мій домашній сервер у моїй мережі —
  мій телефон іде через інший, а той доставляє.
- **Список серверів** вбудований у застосунок, підписаний ключем проєкту й оновлюється з будь-якого
  сервера, з mesh і з GitHub. Домени можуть змінюватись — ключі серверів ні.
- **Переїзд**: людина може змінити домашній сервер, контакти отримають нову адресу через Signal.
- Хто може підняти сервер: питання до власника проєкту (див. «Рішення»).

## 2. Два сервери на шляху (метадані: хто → куди)

- Кожен сервер має ключ шлюзу (уже є). Телефон шифрує запит ключем **сервера-адресата** і
  відправляє його через **сервер-посередник** (інший оператор).
- Посередник бачить IP телефона, але не бачить ні скриньки, ні вмісту. Адресат бачить скриньку,
  але запит прийшов від посередника, а не від телефона.
- Те саме для забирання пошти й сповіщень про нову пошту.
- Вимога: посередник і адресат — **різні оператори**, інакше захисту немає.

## 3. Скриньки на пару й на день (метадані: хто з ким)

- Замість однієї скриньки на людину: скринька для пари контактів, похідна від спільного секрету
  пари (такий уже є для mesh-тегів) і дня. Сервер бачить багато скриньок, що живуть добу й не
  пов'язані між собою.
- Першу скриньку для нових людей (запрошення, «привіт») лишаємо постійною — інакше нового
  контакту не знайти.
- Забирати пошту з багатьох скриньок — одним запитом через посередника.
- Ціна: більше запитів і складніші групи (для груп — скринька на групу, теж змінна).

## 4. Напряму, коли обидва онлайн

- Телефони домовляються через сервер (зашифровано, як дзвінки) і відкривають пряме з'єднання
  (WebRTC data channel, як у дзвінках). Повідомлення, реакції, статуси — без сервера.
- Не вдалося (NAT) або хтось офлайн — звичайний шлях через скриньку.
- Протокол обміну той самий, що в mesh (MeshLink), — це «mesh через інтернет».

## 5. Блокування на рівні мережі

- Кілька доменів і IP для кожного сервера; сервери, що виглядають як звичайні вебсайти (HTTPS).
- Опційно: підключення через Tor або проксі (вимикач у налаштуваннях).
- Останній рубіж — mesh і шлюз: достатньо одного телефона поруч, у якого інтернет працює.

## Свідомо не робимо

- Повністю безсерверну мережу (DHT, як Jami/Briar через інтернет): повідомлення доходять лише
  коли обидва онлайн, а постійне з'єднання на Android з'їдає батарею. Сервери-скриньки лишаються,
  але вони взаємозамінні й нічого не знають.
- Блокчейн і токени.

## Етапи

1. **Кілька серверів у застосунку**: список серверів, перемикання при недоступності,
   будь-який сервер пересилає конверт на домашній сервер адресата.
2. **Федерація**: протокол сервер-сервер, домашні сервери в запрошеннях, переїзд.
3. **Посередник** (два сервери на шляху) для надсилання, забирання й сповіщень.
4. **Скриньки на пару й на день.**
5. **Напряму, коли обидва онлайн.**
6. **Tor/проксі** — опційно.

Етапи 1–2 дають стійкість, 3–4 — захист метаданих, 5 — менше залежності від серверів узагалі.

## Рішення (потрібні від власника проєкту)

- Хто може підняти сервер: лише довірені (список підписує проєкт) чи будь-хто (відкрита федерація)?
- Скільки серверів реально буде на старті й у різних операторів/країнах? Без другого незалежного
  оператора етап 3 нічого не захищає.
- Сповіщення: Android-застосунок уже не залежить від Google (FCM) — він тримає власне з'єднання
  з сервером у фоні. Для етапу 3 це з'єднання теж піде через посередника; чи прийнятна трохи
  більша затримка сповіщень?
