# ADR-0001: Базова архітектура

- Статус: **Пропозиція** (на обговоренні)
- Дата: 2026-11-15

## Контекст

Потрібен месенджер, у якому вже з першого дня закладено: відсутність номера телефону,
мінімум метаданих на сервері, незалежність від транспорту (для майбутнього mesh)
і можливість self-hosting. Ці властивості майже неможливо додати пізніше.

## Рішення

### 1. Ідентичність
- Акаунт = пара ключів (Ed25519) на пристрої. Номер телефону та email не потрібні.
- Нікнейм — необов'язковий, лише для пошуку; контакт можна додати QR-кодом або посиланням.
- Кожен пристрій має власний ключ, підписаний ключем акаунта → кілька пристроїв
  без «головного» телефона.
- Порівняння «кодів безпеки» (safety numbers) для перевірки співрозмовника.

### 2. Криптографія (остаточно — в ADR-0002)
Кандидати:

| | libsignal + OpenMLS | Тільки OpenMLS |
|---|---|---|
| 1:1 чати | Double Ratchet (PQXDH) | MLS-група з 2 учасників |
| Групи | MLS | MLS |
| Ліцензія | **AGPL-3.0** (libsignal) | MIT |
| Офлайн/mesh | Double Ratchet добре терпить безлад у порядку повідомлень | MLS потребує впорядкованих commit-ів → складніше для mesh |
| Постквантовість | PQXDH вже є | є ciphersuite X-Wing (перевірити зрілість) |

**Оновлення 2026-11-15:** проєкт відкритий під AGPL-3.0, тож ліцензія libsignal не заважає.
Попередній вибір: **libsignal для 1:1 + OpenMLS (X-Wing) для груп**.

Ризики, які враховуємо:
- Signal офіційно не підтримує використання libsignal поза Signal; API може змінитися
  без попередження → фіксуємо версію і ховаємо libsignal за власним інтерфейсом у `core/`.
- Ciphersuite X-Wing в OpenMLS ще не має офіційного коду IANA → сумісний лише з
  OpenMLS-клієнтами; для нашої закритої мережі це прийнятно, але потрібен шлях міграції.

Остаточне рішення — в ADR-0002 після прототипу.

### 3. Транспорт
- Ядро оперує **конвертами** (envelope): зашифрований вміст + непрозорий ID поштової скриньки
  отримувача. Формат — Protobuf (деталі в ADR-0003).
- Транспорти — підключувані модулі:
  - Етап 1: WebSocket поверх TLS до сервера.
  - Етап 3: Bluetooth LE, Wi-Fi Direct.
- Модель store-and-forward: повідомлення лежить у черзі, доки не буде доставлене.

### 4. Метадані
- Sealed sender: сервер не бачить відправника.
- Отримувач ідентифікується ротованими ID скриньок, а не ID акаунта.
- Жодних логів IP і зв'язків «хто кому»; доставлені повідомлення видаляються.
- Push-сповіщення без вмісту (лише «прокинься»).

### 5. Стек
- **core/**: Rust (cargo workspace). Біндинги через UniFFI → Kotlin/Swift.
- **server/**: Rust (tokio + axum), PostgreSQL. Docker-образ.
- **clients/**: **Kotlin + Compose Multiplatform** (вирішено 2026-11-15): Android і десктоп
  зі спільним UI, iOS пізніше. Причини: прямий доступ до BLE, Wi-Fi Direct і Android Keystore
  без проміжних шарів (критично для mesh і режиму «під примусом»); офіційні Kotlin-біндинги
  UniFFI до Rust-ядра. Flutter відхилено: платформний код усе одно довелося б писати на Kotlin/Swift.
- Локальна база на пристрої: SQLite із шифруванням (SQLCipher).

### 6. Розгортання
- Збірка — на ПК; на SRV (i3-4030U, 8 ГБ) лише готові образи.
- Ліміти пам'яті для контейнерів, база на SSD.
- Вихід в інтернет — через VPS по WireGuard; SRV напряму не відкритий.
